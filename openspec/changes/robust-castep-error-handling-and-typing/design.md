# Design: Robust CASTEP reader error handling and ExitCode type annotations

## Context

`migrate-castep-reader-to-calcfunction` introduced `read_castep_force_constants` in `workflows/base.py` to read CASTEP force constants in-process as an AiiDA `@calcfunction`. It aimed to catch foreseeable file-reading errors and return `ExitCode(300, ...)` per AiiDA process guidance, allowing callers (`resolve_force_constants`) to report the failure and return `410 ERROR_READ_FAILED`.

However, the initial implementation caught only `EOFError`. Analysis of Euphonic's CASTEP binary reader (`euphonic.readers.castep.read_interpolation_data` and `_read_entry`) reveals multiple exception types raised across common unreadable or invalid inputs:
- `struct.error`: raised when unpacking 4-byte Fortran record markers on files shorter than 4 bytes, or when record boundaries are truncated mid-marker.
- `OSError`: raised when Fortran beginning and ending record markers do not match (`begin != end`).
- `ValueError`: raised when reading a CASTEP file generated by an unsupported CASTEP version (< 17.1), or with an unparseable version string.
- `RuntimeError`: raised specifically when CASTEP did not write force constants (`"Force constants matrix could not be found"`).

Additionally, functions and WorkChain outline methods returning `ExitCode` instances currently omit or under-specify return type annotations.

## Goals / Non-Goals

**Goals:**
- Gracefully handle all foreseeable Euphonic reader failures on corrupt, truncated, or non-phonon CASTEP inputs, consistently returning `ExitCode(300, ...)` from the calcfunction and `410 ERROR_READ_FAILED` from calling workflows.
- Safeguard `RuntimeError` handling so unexpected, non-file-format runtime exceptions continue to propagate as Excepted processes.
- Add explicit, PEP 484 / PEP 604 type annotations (`ExitCode | ...`) for all calcfunctions and workflow methods that can return exit codes.

**Non-Goals:**
- Changing exit code numbers (300 for calcfunction, 410 for workchains).
- Restructuring workchains (left to `refactor-fcwc`).
- Catching bare `Exception`.

## Decisions

### 1. Broadened exception handling with text matching for `RuntimeError`

In `workflows/base.py`:

```python
import struct
from aiida.engine import ExitCode, WorkChain, calcfunction

@calcfunction
def read_castep_force_constants(
    castep_file: SinglefileData,
) -> ForceConstantsData | ExitCode:
    try:
        with castep_file.as_path() as path:
            return ForceConstantsData.from_castep(path)
    except (EOFError, struct.error, OSError, ValueError) as exc:
        return ExitCode(300, f"Could not read CASTEP force constants: {exc}")
    except RuntimeError as exc:
        msg = str(exc)
        if "Force constants matrix could not be found" in msg or "Invalid file" in msg:
            return ExitCode(300, f"Could not read CASTEP force constants: {exc}")
        raise
```

- **Rationale**:
  - `EOFError`, `struct.error`, `OSError`, and `ValueError` are exclusively raised by Euphonic's reader routines on malformed, corrupted, truncated, or incompatible files.
  - `RuntimeError` in Euphonic explicitly flags valid CASTEP outputs where force constants were never written (e.g. standard SCF or relaxation without phonon calculations). Inspecting the error message ensures that genuine internal bugs or unexpected environment errors in Python or native libraries propagate naturally as Excepted processes.
- **Alternatives considered**:
  - *Catching bare `Exception`*: Rejected; violates AiiDA's recommendation to catch only foreseeable and classifiable errors, masking potential bugs.
  - *Catching unconditional `RuntimeError`*: Rejected; `RuntimeError` can be raised by lower-level C extensions or internal system faults where an Excepted state is appropriate.

### 2. Type annotation of ExitCode-returning functions and methods

- Update `read_castep_force_constants` to return `ForceConstantsData | ExitCode`.
- Annotate WorkChain outline step methods that return failure exit codes:
  - `ForceConstantsWorkChain.resolve_force_constants(self) -> ExitCode | None`
  - `DispersionWorkChain.finalize(self) -> ExitCode | None`
  - `DosWorkChain.finalize(self) -> ExitCode | None`
  - `ToscaFromModesWorkChain.finalize(self) -> ExitCode | None`
  - `ToscaFromForceConstantsWorkChain.compute_spectrum(self) -> ToContext | ExitCode | None`
  - `ToscaFromForceConstantsWorkChain.finalize(self) -> ExitCode | None`
- **Rationale**: Makes error paths explicit for typecheckers and callers, adhering to modern typing guidelines in Python 3.12 without affecting AiiDA's runtime outline parser.

## Risks / Trade-offs

- [Risk: Upstream Euphonic changes the exact phrasing in `RuntimeError`.] → Mitigation: Match core substrings (`"Force constants matrix could not be found"` and `"Invalid file"`). Verify against current pinned Euphonic (`~=2.0`).
- [Risk: WorkChain outline runner expects `None` or `ExitCode` or `ToContext` and annotations could interfere.] → Mitigation: Python typing annotations do not modify runtime method attributes. The test suite verifies that outline execution remains identical.
